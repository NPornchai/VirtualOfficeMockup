⚡Executive Summary

The VirtualOfficeMockup is a working React 19 + TypeScript frontend with a minimal Express 4 backend (2 Gemini proxy endpoints, 184 lines). The goal is to evolve it into a Personal Claude Code Orchestration Dashboard — a web UI to manage projects, configure global + project agents, and drive real Claude Code runs with live streaming output, on top of an existing per-project context-files workflow.

Recommendation Extend Express with better-sqlite3, Node child_process, and SSE. Drive Claude Code via claude -p --output-format stream-json. Model agents as global with optional project-scoped overrides. Treat each project's CLAUDE.md + .claude/context/ as source-of-truth project memory. Do not add .NET. Estimated: 3–4 weeks, 7 phases incl. Phase 0 spike.

🧠Two Memory Layers

The orchestrator and Claude Code each maintain state. Keep them distinct — do not let one duplicate the other:

Layer 1 — Run / Session
SQLite runs.session_id
  • Scope: per run-chain
  • Owner: Orchestrator
  • Purpose: conversation transcript continuity
  • --resume a recent session
  • Short-term transcript glue
Layer 2 — Project Memory
CLAUDE.md + .claude/context/*
  • Scope: per project, long-lived, git-committed
  • Owner: the agents (per their write rules)
  • Purpose: human/agent-readable narrative
  • Read at START of every run (auto-loaded)
  • Rewritten at END of every session
Key rule The DB never stores context-file content — it points at the project path and reads them on demand. CLAUDE.md is auto-loaded by Claude Code, so every run already gets the project's rules without any orchestrator injection.

⚖️Architecture Decision: .NET vs Node

ทำไมไม่เพิ่ม .NET — overhead ไม่คุ้มกับ single-user tool และ Claude Code SDK เป็น TS/Python (ไม่มี .NET SDK)

✓ RECOMMENDED Extend Express (Node)
  • child_process.spawn('claude') native — no interop
  • better-sqlite3 synchronous, zero-config
  • SSE with built-in response — zero extra packages
  • One TypeScript language, one runtime, one process
  • Upgrade path: @anthropic-ai/claude-agent-sdk (TS)
✗ NOT RECOMMENDED ASP.NET Core
  • Two runtimes, two processes, two ports, CORS
  • No .NET Claude Code SDK — hand-parse stream-json
  • EF Core migrations — overhead vs direct SQLite
  • No capability advantage at this scale
  • SignalR ≈ SSE here; not worth the overhead

🗄SQLite Schema

CREATE TABLE projects (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT    NOT NULL,
    path        TEXT    NOT NULL,           -- absolute cwd passed to `claude`
    git_remote  TEXT,
    description TEXT,
    created_at  TEXT    NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE agents (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    scope           TEXT    NOT NULL DEFAULT 'global',  -- 'global' | 'project'
    project_id      INTEGER REFERENCES projects(id) ON DELETE CASCADE,  -- NULL when global
    name            TEXT    NOT NULL,
    role            TEXT    NOT NULL,
    model           TEXT    NOT NULL DEFAULT 'claude-sonnet-4-6',
    system_prompt   TEXT,
    allowed_tools   TEXT,                    -- CSV e.g. 'Read,Edit,Write,Bash'; NULL = inherit
    permission_mode TEXT    NOT NULL DEFAULT 'acceptEdits',
    created_at      TEXT    NOT NULL DEFAULT (datetime('now')),
    CHECK ( (scope = 'global'  AND project_id IS NULL)
          OR (scope = 'project' AND project_id IS NOT NULL) )
);
CREATE UNIQUE INDEX idx_agents_global_name ON agents(name) WHERE scope = 'global';

CREATE TABLE runs (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id   INTEGER NOT NULL REFERENCES projects(id),
    agent_id     INTEGER NOT NULL REFERENCES agents(id),
    prompt       TEXT    NOT NULL,
    output       TEXT,                          -- accumulated stream-json transcript
    session_id   TEXT,                          -- from init event; used for --resume
    resume_of    INTEGER REFERENCES runs(id),   -- NULL = fresh session
    status       TEXT    NOT NULL DEFAULT 'running',
    exit_code    INTEGER,
    started_at   TEXT    NOT NULL DEFAULT (datetime('now')),
    finished_at  TEXT
);
-- status: 'running' | 'done' | 'cancelled' | 'error'

CREATE INDEX idx_agents_project ON agents(project_id);
CREATE INDEX idx_runs_project   ON runs(project_id);
CREATE INDEX idx_runs_agent     ON runs(agent_id);
CREATE INDEX idx_runs_session   ON runs(session_id);

⌨️Claude Code Integration

A. Project Memory — Auto-loaded, In-repo

<project-root>/
├── CLAUDE.md                     ← auto-loaded by Claude Code every session
└── .claude/context/
    ├── current-task.md           ← forward-looking; overwrite each session
    ├── handoff.md                ← backward-looking; overwrite each session
    └── decisions.md              ← append-only trade-off log
Key insight Because CLAUDE.md is auto-loaded, every run already gets the project's rules and the end-of-session write rules — the orchestrator does not inject them. The dashboard reads these files on demand and shows them in the project view. New project → offer Bootstrap.

B. Agent Identity — Global vs Project Subagents

~/.claude/agents/ — available everywhere
Global Agents
  • → senior-dev, code-reviewer
  • → DB scope = 'global', project_id = NULL
  • → Export: ~/.claude/agents/<name>.md
  • → Work in any project out of the box
.claude/agents/ — per-repo override
Project Agents
  • → DB scope = 'project', project_id = X
  • → Export: .claude/agents/<name>.md
  • → Win on name collision with global
  • → Specialised config for one project
Source of truth The DB is the source of truth for agent config. Runs apply it deterministically via CLI flags at spawn time — so the run is that agent regardless of file state. POST /api/agents/:id/export mirrors the record to the matching .md so the same agents also work in a plain terminal.

C. Run Mechanics — Spawn, Stream, Session

claude -p "<prompt>" \
  --append-system-prompt "<agent.system_prompt>" \
  --model "<agent.model>" \
  --allowedTools "<agent.allowed_tools>" \
  --permission-mode "<agent.permission_mode>" \
  --output-format stream-json \
  [--resume <session_id>]
# cwd = projects.path

stream-json = NDJSON: system/init (carries session_id), assistant, tool_use, tool_result, final result. Read line-by-line → forward each as SSE message → persist session_id on init → set status/exit_code/finished_at on exit.

Process Lifecycle Edge Cases

Validate in Phase 0 / Phase 2
  • • session_id timing — appears in init (persist immediately) and again in result
  • • Non-zero exit — store exit_code; distinguish crash / clean / cancel
  • • Line boundaries — split bytes on \n, JSON.parse per line
  • • Cancellation on Windows — SIGTERM unreliable; use proc.kill() and verify
  • • Concurrent runs — processMap keyed by runId; cap concurrency

🔒Security (Single-user, Localhost)

Important acceptEdits / bypassPermissions let an agent edit files and run bash without prompting — this is arbitrary local code execution from a web request.
RuleDetail
Bind to 127.0.0.1 onlyNever 0.0.0.0. Do not expose the port externally.

✅Conclusion

Two changes define rev3: agents are global (with optional project overrides), matching how senior-dev and code-reviewer are actually used; and each project's context-files system is the in-repo source-of-truth memory the dashboard surfaces but never duplicates. The orchestrator's own state stays minimal — projects, agent configs, and run history with session_id for resume. Everything else (the project narrative, the working rules) already lives in the repo via CLAUDE.md and .claude/context/, read at the start of every run and maintained at the end.

Next Action — Phase 0 Spike Prove that claude -p --output-format stream-json → SSE → session_id → --resume works on your Windows machine before writing any schema or UI. This de-risks the entire architecture before committing to build phases 1–6.
