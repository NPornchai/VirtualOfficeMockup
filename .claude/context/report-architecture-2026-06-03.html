⚡Executive Summary

The VirtualOfficeMockup is a working React 19 + TypeScript frontend with a minimal Express 4 backend (2 Gemini proxy endpoints, 184 lines). The goal is to evolve it into a Personal Claude Code Orchestration Dashboard — a web UI to manage projects, configure agents, and drive real claude CLI runs with live streaming output.

Recommendation Extend the existing Express backend with better-sqlite3, ws, and Node built-in child_process. Do not add .NET. Estimated full build: 3–4 weeks across 6 phases.

⚖️Architecture Decision: .NET vs Node

ทำไมถึงไม่เพิ่ม .NET — เหตุผลหลักคือ overhead ไม่คุ้มกับ single-user personal tool

✓ RECOMMENDED Option A — Extend Express
  • child_process.spawn('claude') is native Node — no wrappers
  • better-sqlite3 — synchronous, zero-config, no server process
  • ws streams stdout in ~5 lines of code
  • Same TypeScript across frontend and backend
  • One runtime, one process, one npm run dev
  • Deploy: copy folder, node server.js
✗ NOT RECOMMENDED Option B — ASP.NET Core
  • Two runtimes (Node for frontend, .NET for backend)
  • Two processes in production, two ports, CORS required
  • EF Core migrations — overhead vs direct SQLite
  • No capability advantage for a personal single-user tool
  • +2–3 days setup, ongoing deployment friction
  • SignalR ≈ ws for this use case; not worth it alone
Decision Option A. The problem does not justify two runtimes.

🗄SQLite Schema

CREATE TABLE projects (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT    NOT NULL,
    path        TEXT    NOT NULL,
    git_remote  TEXT,
    description TEXT,
    created_at  TEXT    NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE agents (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id    INTEGER NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    name          TEXT    NOT NULL,
    role          TEXT    NOT NULL,
    model         TEXT    NOT NULL DEFAULT 'claude-sonnet-4-6',
    system_prompt TEXT,
    created_at    TEXT    NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE runs (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    agent_id    INTEGER NOT NULL REFERENCES agents(id),
    prompt      TEXT    NOT NULL,
    output      TEXT,
    status      TEXT    NOT NULL DEFAULT 'running',
    started_at  TEXT    NOT NULL DEFAULT (datetime('now')),
    finished_at TEXT
);

-- status values: 'running' | 'done' | 'cancelled' | 'error'

WebSocket Protocol

ws://localhost:PORT/ws

Client sends:  { type: 'subscribe', runId: number }

Server sends:  { type: 'stdout', runId, line: string }
               { type: 'done',   runId, status: 'done' | 'error' }

⌨️Claude Code CLI Integration

System Prompt Delivery (in order of preference)

1ST
Write CLAUDE.md into project directory before spawning
Picked up automatically by Claude Code — cleanest approach
2ND
Prepend system prompt to the user prompt string
Simple fallback, no file I/O required
3RD
Use --system-prompt flag if CLI version supports it
Verify at runtime with claude --help

Process Lifecycle Edge Cases

Validate in Phase 2
  • • Exit code non-zero — distinguish crash from user-initiated error
  • • Output buffering — data events don't guarantee line boundaries; buffer and split on \n
  • • Cancellation on Windows — SIGTERM may not work; use proc.kill() and verify
  • • Concurrent runs — processMap keyed by runId; cap max concurrent to avoid OOM

✅Conclusion

The VirtualOfficeMockup has a solid frontend foundation and a deliberately minimal backend — which is an advantage, not a liability. Extending it to a real orchestration dashboard requires adding exactly three capabilities: a SQLite layer, a WebSocket server, and a process manager that spawns the claude CLI. None of these require changing the language, the framework, or the deployment model.

The Gemini API dependency can be removed entirely once Phase 2 is complete — it serves no purpose in the target architecture. The visual room metaphor is optional to keep; repurposing rooms as feature sections is the lowest-friction path.
